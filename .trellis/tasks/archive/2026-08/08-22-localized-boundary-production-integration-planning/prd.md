# MR9 Localized Boundary Interaction Production Integration Planning

## Goal

Produce a repository-grounded plan for the minimum production Main Window integration of the Browser Lab-falsified localized boundary response and subordinate halo. The plan must preserve the accepted visual behavior, retain one Expanded presentation renderer/runtime authority, and stop before implementation or Architecture PASS.

## Background And Confirmed Constraints

- The accepted renderer baseline is the 2D Multi-Temperature Thermal interior plus Refraction, with warm-frontier contact at the real panel boundary.
- The localized boundary response and its contact-driven subordinate halo have passed Browser Lab falsification.
- The verified layer geometry is a 228x228 transparent outer domain containing the real 200x200, radius-16 interactive panel at `(14, 14)`.
- Halo support is bounded to 12px beyond the real panel boundary and the outermost 2px must remain strictly zero.
- Expanded presentation keeps exactly one `ExpandedPresentationSurface`, one canvas, one WebGL program, one draw path, and one runtime authority.
- Reduced Motion permits no continuing frames.
- Paper processed morphology/palette and absolute `E × boundaryBand` are closed directions.
- Traversal, Entry, and Exit redesign remain parked.
- The MR9 worktree contains uncommitted Browser Lab spike changes and evidence that must be preserved during planning.
- Repository evidence confirms Windows/macOS production already owns a stable 228x228 native viewport around the 200px panel; no native resize is required.
- In Full mode the native 228px BrowserWindow remains a rectangular hit target. The transparent gutter is panel-noninteractive in the DOM, but it is not claimed to be OS click-through.

## Requirements

1. Compare the current production 200-domain canvas, radius-16 panel clip, CSS shadow, and interaction/drag composition with the verified 228-domain Lab layer model using repository file/line evidence.
2. Assign one owner for the 228x228 transparent outer FX domain while preserving the real 200x200, radius-16 panel as the only visible interactive panel.
3. Preserve one CSS shadow authority and prevent shell, canvas, and clip layers from becoming duplicate visual authorities.
4. Define pointer, drag, drop, hit-testing, and transparent-gutter semantics for the 14px outer inset on each side.
5. Reuse existing production activation, runtime scheduling, Refraction, Interior, and Reduced Motion authorities. Add no lifecycle or state authority unless repository evidence proves an unavoidable requirement.
6. Treat boundary/halo behavior as a fixed Expanded renderer capability unless repository evidence proves it needs Product or Application state.
7. Define Windows production transparent-window validation and explicitly mark macOS host behavior `NOT VERIFIED` when no macOS host is available.
8. Define the smallest implementation surface, ordered integration sequence, validation gates, and an immediate rollback/fallback boundary.
9. Do not redesign shader morphology or alter accepted visual parameters unless the production coordinate/unit mapping demonstrably changes their physical meaning.
10. Produce planning artifacts only, then stop for GPT Architecture Lead Planning Review without starting the Trellis task or granting Architecture PASS.
11. Preserve a 200-domain Interior+Refraction fallback on platforms whose existing geometry exposes no 14px outer gutter; do not widen native scope in this task.

## Acceptance Criteria

- [ ] A repository-grounded Planning Report names the current production and Lab ownership boundaries with file/line anchors.
- [ ] The report defines exactly one 228 outer FX owner, one real 200/r16 interactive panel owner, one CSS shadow authority, and one renderer/runtime authority.
- [ ] Pointer, window drag, file-drop, hit-testing, and transparent-gutter behavior are specified as observable production semantics.
- [ ] The design shows why no new Product/Application/lifecycle state is required, or records narrow repository evidence if any such state is unavoidable.
- [ ] Reduced Motion has zero continuing frames and reuses the existing invalidation/scheduling contract.
- [ ] Windows validation covers real transparent-window composition, outer-gutter alpha, panel geometry, interaction, drag/drop, CSS shadow exclusivity, and lifecycle behavior.
- [ ] macOS is explicitly scoped as `NOT VERIFIED` without a host, with no implied cross-platform PASS.
- [ ] The rollback/fallback boundary can remove the localized boundary/halo production integration without disturbing the accepted Interior, Refraction, or existing Expanded lifecycle/state authorities.
- [ ] `prd.md`, `design.md`, and `implement.md` converge with no blocking open question and no implementation changes.

## Out Of Scope

- Shader morphology exploration or visual retuning.
- Paper processed morphology/palette.
- Absolute `E × boundaryBand`.
- Traversal, Entry, or Exit redesign.
- New presentation modes, Product/Application features, or lifecycle authorities.
- Implementation, task activation, commit, archive, or Architecture PASS.
